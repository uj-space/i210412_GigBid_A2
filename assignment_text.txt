Overview
You will ship GigBid, a deployed web application in which a team of LangGraph agents finds freelance 
jobs, judges whether they are worth bidding on, writes proposals grounded in real portfolio evidence, and 
manages client conversations, with a human approving every proposal and message before it leaves the 
system. It connects to a provided marketplace simulator for development and grading, and to Upwork’s 
official MCP server for real use.
This is a product, not a notebook. When you finish, you can point GigBid at your own profile and use it to 
win work. That is the test of whether you built it well.

1.Build and consume MCP servers, including a remote, OAuth-protected third-party server, behind a
clean adapter so the system works against a simulator and a live marketplace.
2.Implement advanced RAG (hybrid, reranked, outcome-aware, claim-verified) and choose a design 
by measurement.
3.Architect a multi-agent LangGraph system with parallel branches, critique loops, human approval,
persistence and long-term memory.
4.Build a full-stack web interface that streams agent progress and lets a human approve, edit or 
reject agent actions.
5.Operate the system: scheduling, evaluation in CI, tracing, guardrails, budgets and deployment.

The Product: GigBid
The problem. Freelancers can spend hours scanning job feeds, use paid Connects on jobs they are unlikely 
to win, send generic proposals that clients ignore, and encounter scam posts requesting free work or off-
platform payment. GigBid handles discovery, assessment, and drafting; the freelancer makes the 
decisions.
The user journey.
1.The freelancer signs in, connects a marketplace account, uploads a portfolio (CV, case studies, 
GitHub repos, past proposals with outcomes) and sets rates, filters and a weekly Connects budget.
2.Every few hours GigBid pulls new jobs from saved searches, analyses each one, flags risks, scores 
fit, recommends a bid or a skip, and suggests a price.
3.For a recommended job, GigBid drafts a proposal and screening answers in which every claim 
links to portfolio evidence. A critic checks it; a compliance guard checks platform rules.
4.The freelancer edits and approves; only then is the proposal sent to the marketplace as a draft for 
final confirmation.
5.When a client replies, GigBid drafts a response, proposes interview slots from the calendar, and 
keeps the pipeline board current. Outcomes feed back into what GigBid learns.

Models: Open and Local First
Every student must be able to run GigBid end to end without paying for an API. The skill employers want 
is building a strong system on a small budget, so open-weight and local models are the default and paid 
frontier models are an optional extra.
Rules.
•Two profiles in agent/config.yaml . open is required: open-weight models only, run locally 
(Ollama, vLLM or llama.cpp) or through a hosted open-model provider. paid is optional: any API 
model, used only where it beats the open profile enough to justify its cost.
•The deployed link must work on the open profile. Since free hosts have no GPU, the 
deployment may call a hosted open-model provider (for example Groq, OpenRouter or Together; 
check their current free-tier limits).
•Embeddings and reranker are open models in both profiles.  They run acceptably on a CPU.
•Route by node. Cheap, frequent nodes (Scout, Risk Assessor, intent and compliance checks) run on
a small model; Writer and Critic get the strongest model you can afford. Every node’s model is set 
in config, never in code.
•Choose by measurement.  Compare at least two open LLM configurations on the dev set before 
choosing, and report quality, latency and cost for each profile you run: USD for APIs, and 
hardware plus tokens per second for local models.
•Free GPUs on Google Colab or Kaggle are fine for running evaluations.

Agents never call GigSim, Upwork, a database or a file directly. Every capability is an MCP tool with a 
schema, an owner and a test. Your Portfolio server should be good enough that another freelancer could 
plug it into Claude Desktop or Cursor and use it.

•Tools: search_evidence(requirement, k, filters)  returning evidence items with

Part B — Advanced RAG: Evidence, Not Vibes (20 marks)
A winning proposal proves fit with specific, true evidence. Retrieval decides which evidence the writer 
sees, and verification decides whether the writer told the truth. The persona corpora are built to defeat 
naive RAG: code and prose mixed, the same project described three ways, skills implied rather than 
named, and past proposals whose outcome matters more than their wording.
B1. Ingestion. Loaders for PDF CVs, Markdown case studies, repo READMEs and code (through the GitHub
MCP server), reviews and past proposals. Metadata on every chunk: persona, type, project, skills, date, 
client industry and, for proposals, outcome. Incremental re-indexing when the user adds work in the UI.

Part C — Multi-Agent Orchestration in LangGraph (25 marks)
You wire the nine roles into two durable graphs that can pause for a human, survive a crash, learn from 
outcomes and explain every decision.
C1. Two graphs, one state discipline.
•Bid graph (one thread per job): Scout hands a job in; Job Analyst, Risk Assessor and Fit Matcher 
run in parallel with Send; a decision node chooses skip, watch or bid; Pricing Strategist, Proposal 
Writer, claim verification, Critic and Compliance Guard follow; the graph interrupts for approval 
before anything is sent.
•Conversation graph  (one thread per client conversation): Client Liaison reads new messages, 
classifies intent (question, negotiation, interview request, scam signal), drafts a reply or interview 
slots, and interrupts for approval.
C2. State design. Typed state (TypedDict or Pydantic) with separate fields for the job, analyses, evidence, 
decision, price, drafts, critiques, approvals and outcomes; reducers wherever parallel branches write. 
Keep three things apart and say so in your report:
•State: what this job or conversation needs right now.
•Execution trace: every tool name, argument, result and observation, kept for audit and 
debugging.
•Long-term memory : only promoted knowledge, written to a LangGraph store by an explicit rule. 
Two stores are required: a style memory learned from the user’s edits to drafts (“always cut the 
first sentence”, “never say passionate”), and an outcome memory of what won or got replies per 
job category. Raw tool output never goes straight into memory.
C3. Structured hand-offs.  Agents exchange Pydantic objects ( JobSpec, RiskReport, FitReport, 
BidDecision, PriceQuote, ProposalDraft, Critique, ComplianceVerdict ), not free text, 
for anything a later step decides on.
C4. Loops with limits.  The Critic can send a draft back at most twice; the Compliance Guard can block, 
with a reason shown in the UI. A step budget and a token budget per thread; exceeding either moves the 
thread to a visible “needs attention” state.
C5. Human in the loop.  interrupt() before submitting a proposal, sending a message or spending 
Connects. The approval payload carries the draft, the evidence behind every claim, the risk report, the 
price rationale and the dry_run preview. The user can approve, edit (edits are diffed, saved for style 
memory and re-checked by Compliance) or reject with a reason. A per-user autonomy setting may allow 
auto-skip of low-fit jobs, but never auto-send.

Part E — Production Engineering (10 marks)
E1. Scheduling and background work.  Scouting and long agent runs execute in a worker (Celery, Arq or 
Dramatiq on Redis), not inside web requests. Each saved search has a schedule; live mode uses a 
conservative interval you justify in docs/RUNBOOK.md . Jobs are processed idempotently, so a worker 
restart never double-analyses or double-submits.
E2. Evaluation in CI.  make eval runs retrieval metrics, decision metrics and a fixed GigSim reply-rate 
run, and writes evals/results/*.json . GitHub Actions runs unit, contract and Playwright tests plus
a 30-job smoke eval on every pull request, and fails if unsupported claims rise or bid-or-skip F1 drops past 
thresholds you set.
E3. Observability. LangSmith, or self-hosted Langfuse or Arize Phoenix. One trace id flows from the UI 
request through the API, the graph, every MCP server and the audit log. Each trace shows tokens and cost 
per node.
E4. Guardrails.
•Job posts and client messages are untrusted data: delimit them, never follow instructions inside 
them, and test with the planted-injection jobs (report attack success rate before and after 
defences).
•Mask emails, phone numbers and payment details in logs and traces.
•Store OAuth tokens encrypted; never log them; scope each user’s data by tenant in every query.
E5. Budgets. Declare p95 latency and cost per job analysed and per proposal. Report measured values on 
the hidden test run and one optimisation that helped (a small model for routing and risk, caching 
evidence, prompt trimming, skipping early).
E6. Packaging and deployment.  docker compose up  starts web, API, worker, MCP servers, GigSim, 
Postgres, Redis, the vector store and an Ollama service for the open profile. Secrets only from environment
variables; commit .env.example, never .env. Deploy to any public host and keep it live until grades 
are released, with a reviewer login preloaded with a persona.
